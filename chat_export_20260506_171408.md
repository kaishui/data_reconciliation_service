## Phase 3: CDC Pipeline Design

### Connector Selection

- **MongoDB**: `flink-connector-mongodb-cdc` (Flink CDC 3.x, based on MongoDB change streams)

  - Resume tokens for exactly-once semantics
- **PostgreSQL (future)**: `flink-connector-postgres-cdc` (based on pgoutput / WAL decoding)

### Change Event Schema

Unified internal model (database-agnostic):

```java
public class ChangeEvent {
    String documentKey;          // _id (MongoDB) or primary key (PG)
    String collectionName;       // collection or table name
    OperationType op;            // INSERT, UPDATE, DELETE, REPLACE
    Map<String, Object> before;  // pre-image (nullable)
    Map<String, Object> after;   // post-image (nullable)
    String sourceCluster;        // where the change originated
    Long eventTimestamp;         // CDC event time (wall clock)
    Long dataTimestamp;          // user-configured timestamp field value
    Long sourceTsMs;             // source cluster's operation time
}
```

| Scenario | sourceCluster value | Action |
|---|---|---|
| User writes to GCP directly | `"gcp"` | GCP CDC emits, syncs to HIC |
| User writes to HIC directly | `"hic"` | HIC CDC emits, syncs to GCP |
| GCP sync writes to HIC | `"gcp"` (preserved) | HIC CDC sees `"gcp"` → **DROP** |
| HIC sync writes to GCP | `"hic"` (preserved) | GCP CDC sees `"hic"` → **DROP** |

Loop prevention is a filter in each Flink job:

```java
public class LoopPreventionFilter extends RichFilterFunction<ChangeEvent> {
    private final String localCluster;  // "gcp" for GCP→HIC job, "hic" for HIC→GCP job
    
    @Override
    public boolean filter(ChangeEvent event) {
        // Drop events that originated from the REMOTE cluster
        // (they were already synced by the other direction's job)
        return !Objects.equals(event.getSourceCluster(), remoteCluster());
    }
}
```

### Strategy Interface

```java
public interface ConflictStrategy {
    /** Strategy identifier (used in config) */
    String name();

     * Resolve a conflict between source and target versions.
     * @return resolved document, or null to skip this write
     */
    Map<String, Object> resolve(ConflictContext ctx);
}

public class ConflictContext {
    String documentKey;
    String collectionName;
    Map<String, Object> sourceVersion;   // incoming from CDC
    Map<String, Object> targetVersion;   // current in target DB
    Long sourceTimestamp;                // from configured timestamp field
    Long targetTimestamp;
    String sourceCluster;                // "gcp" or "hic"
    Map<String, Object> metadata;        // strategy-specific params
}
```

### Strategies (Phase 1)

```
LAST_WRITE_WINS       — compare dataTimestamp, newest wins
SOURCE_PRIORITY       — configured cluster always wins (e.g., GCP is master)
TARGET_PRIORITY       — target cluster always wins (HIC is master)
MANUAL                — log conflict, skip write, queue for human review
```

### Sliding Window Semantics

The sliding window is implemented as a Flink `KeyedProcessFunction` with state:

```java
public class WindowedConflictResolver extends 
    KeyedProcessFunction<String, ChangeEvent, ChangeEvent> {
    
    // State: buffer of pending events per document key
    private ValueState<Map<String, List<ChangeEvent>>> windowBuffer;
    // State: timer for window expiration
    private ValueState<Long> windowTimer;
    
    private final long windowSizeMs;       // e.g., 30_000 (30 seconds)
    private final ConflictStrategy strategy;
    private final String timestampField;
    
    @Override
    public void processElement(ChangeEvent event, Context ctx, Collector<ChangeEvent> out) {
        // 1. Buffer event in window
        // 2. Register/update timer for windowSizeMs from event time
        // 3. On timer: drain window, resolve conflicts, emit resolved events
    }
    
    @Override
    public void onTimer(long timestamp, OnTimerContext ctx, Collector<ChangeEvent> out) {
        // 1. Collect all buffered events for this key
        // 2. Check against target DB (query current version)
        // 3. If conflict: apply strategy, log to audit
        // 4. Emit resolved event to sink
        // 5. Clear state
    }
}
```

**Why a window?** CDC events may arrive out of order. If user updates document D on GCP at T1 and HIC at T2 (where T2 > T1), but the GCP CDC event arrives 5 seconds later than the HIC event, without a window we might write the older version last, losing the newer one. The window buffers all versions of a key, then picks the winner once the window closes.

## Phase 7: SourceCluster Injection and Loop Prevention

### Write-time injection

The MongoDB sink always sets `sourceCluster` to the **source cluster label**:

```java
public class SourceClusterInjector implements MongoSinkDocumentTransformer {
    
    @Override
    public Document transform(Document doc, ChangeEvent event) {
        // sourceCluster reflects where the data ACTUALLY last changed by a user
        // For GCP→HIC job: sourceCluster = "gcp"
        // For HIC→GCP job: sourceCluster = "hic"
        doc.put("sourceCluster", sourceClusterLabel);
        return doc;
    }
}
```

### Read-time filter (loop prevention)

Each Flink job's CDC source filters out changes that the other job wrote:

```java
// In the CDC deserialization or as a filter step
// GCP→HIC job: skip events where sourceCluster == "hic"  
// HIC→GCP job: skip events where sourceCluster == "gcp"
```

This guarantees no event crosses a cluster boundary more than once.

### Edge case: User clears sourceCluster

If a user manually sets `sourceCluster` to null or deletes it, the change will be re-synced (potentially creating a loop). Mitigation:
- MongoDB change stream's `updateDescription.updatedFields` can detect if `sourceCluster` was modified
- If `sourceCluster` was explicitly modified in this event, treat it as `null` (re-sync)
- Or: add a schema validation rule that prevents clearing `sourceCluster`

### PostgreSQL-specific considerations

| Concern | MongoDB handling | PostgreSQL handling |
|---|---|---|
| Primary key | `_id` (ObjectId/String) | Composite or single-column PK |
| Change stream | `$changeStream` | WAL decoding (pgoutput plugin) |
| Schema evolution | Schemaless, handles new fields | Requires DDL handling / schema registry |
| Timestamp field | Any document field | Column of type `TIMESTAMP` |
| sourceCluster | Document field | Dedicated column `source_cluster VARCHAR(50)` |

The `ChangeEvent` model already abstracts these: `documentKey` can be a string (MongoDB ObjectId) or a `Map<String, Object>` (PostgreSQL composite key), and the strategy layer operates on `Map<String, Object>` (MongoDB documents) or `Row` objects (PostgreSQL rows).

### Key design points implemented in code

- **Loop prevention**: `LoopPreventionFilter` drops events where `sourceCluster == remoteClusterLabel`
- **Sliding window**: `WindowedConflictResolver` buffers per-key events, fires timer on expiry, picks winner by `dataTimestamp`
